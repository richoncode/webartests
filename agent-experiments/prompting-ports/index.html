Porting Playbook

Prompting a Port

Moving a project to another language or platform with a coding agent, without burning the team's familiarity with the code. A port is a translation, not a rewrite: an agent left to its own judgement improves the code, and every improvement costs a programmer who knows the original the ability to read the new one.

You type three prompts. §1 is the procedure, four steps; §5 is the prompts. Everything else is folded shut with a line on the lid saying why you might open it, and you can run a port without opening any of it.

§1The Recipe
Four steps, no setup

Nothing to install, nothing to configure. Copy one prompt to begin; after that you type a single word.

  1. 1
    Copy START and paste it in your source project
    Use the Copy button in §5, not a text selection — the button carries the contract and all fifteen step prompts with it. START works the rest out from the tree and asks one thing: what language and platform are we porting to?
  2. 2
    Read the first batch, then stop watching
    Open two diffs. Look for renames, extracted helpers, added null checks, a swapped data structure — and correct anything with the matching row from §12. Then leave it alone. Supervising the second package costs what an attended port costs.
  3. 3
    Come back, answer, paste CONTINUE
    It pauses when it needs you, printing links in priority order with any questions already grouped. Answer in the conversation, paste CONTINUE, go away again. Repeat for as long as it takes. When nothing is left to port, CONTINUE says so rather than starting something.
  4. 4
    Paste FINISH
    Fifteen checks, each PASS or FAIL, running the real target suite against the frozen baseline. On FAIL it reports and waits — you decide, paste CONTINUE, run it again. On COMPLETE it commits, closes the log and removes the contract.

§2Vocabulary
Fix these two words first

Source and target, defined. Open it if a prompt’s wording ever seems ambiguous.

Every prompt here uses two words in one fixed sense. The contract fixes them at the top of each session, which is the only thing that stops them drifting.

Source
The original version — its language, its platform, its directory tree, its tests. The source is the specification. It is authoritative even where it is ugly, and especially where it is surprising.
Target
The new version — the language and platform being ported to. The target owes the source a resemblance. It earns a difference only by necessity, and only with that necessity written down at the site of the difference.
§3The Eight Standing Goals
What the prompts protect

What the method protects and why each rule exists. Open it to argue with the approach, or to explain it to someone else.
  1. 01
    Preserve momentum of familiarity
    Keep the target core code as close to identical to the source as the target language permits. A programmer who knows the source opens the target file and recognises it — same declarations in the same order, same branches, same early returns, same comments. This goal outranks elegance, idiom, and the agent's taste. It is the reason the port is worth doing at all.
  2. 02
    Parallel trees
    Place the target directory at a level that lets the source and target trees sit side by side, one target directory per source directory at the same relative path. Two windows, same scroll position, same file — that is the working posture the whole port is optimised for.
  3. 03
    Parallel names
    Mirror file names, class names, property names, method names, constants, enum cases, and test names. Change casing only where the target language's convention forces it, and change only the casing — never the word. A renamed method is a broken search across two repositories.
  4. 04
    Port the tests that prove it
    Where the source carries tests that validate the implementation, port those tests alongside the code they cover, with the same test names, the same assertions in the same order, and byte-identical fixtures. Run the source suite before the port starts and keep that result as a fixed baseline — a ported test is judged against what the source test did, not against green. A source test already failing or skipped at baseline is not evidence of anything, and finding that out now beats discovering it through a target failure everyone assumes the port caused.
  5. 05
    Replace a missing API deliberately
    When the target platform has no parallel for a source API, size it honestly. Small and self-contained: build it, document it back to the source API and its docs, say why it exists, and test it. Large or subtle: stop, research credible libraries, and open a conversation before writing a line. See §8.
  6. 06
    Keep a living scorecard
    Maintain one progress report throughout — a collapsible directory/file hierarchy mirroring the source tree, each file carrying a status, each directory carrying a rolled-up score. Update it as work lands and audit it against disk on a schedule. See §9.
  7. 07
    Run unattended where coverage allows
    A port of any real size is only finishable if the agent can work in long autonomous runs. Let it: batch whole packages wherever source tests exist and passed at baseline, since the ported suite checks every file as it lands and never tires. Close each batch with a commit, and write the commit hash, a source-against-target diff link, and the paired test results onto every scorecard row. Review from those links afterwards. Keep the one-file-at-a-time discipline for code with no coverage, where reading it is the only check that exists. The three prompts that do all of this are §5.
  8. 08
    Let uncertainty travel
    An agent that cannot cheaply say "I did not understand this" will invent a reading, and the invention is indistinguishable from the rest of the port. Give it two inline markers — PORT-DEVIATION for a difference it decided on, PORT-QUESTION for one it could not — both naming the source file and line. Gather every question into a band at the top of the scorecard. The run continues; the doubt reaches a human. See §10.
§4Prompt Strategy
Why the prompts are shaped this way

The failure each prompt is worded to prevent. Open it before you edit one.
Strategy What it buys, and what it costs to skip
State the contract, then re-anchor Install the port contract (CONTRACT) where the CLI loads it at the start of every session, rather than pasting it once at the start of the project. Fidelity rules decay across a long context; the agent that was translating faithfully at file 10 is refactoring by file 40, and a resumed session starts with none of it.
Read before write Make the agent read the source file in full and enumerate what it is about to create before it creates anything. The enumeration is a cheap checkpoint: if the list does not match the source one-for-one, stop it there rather than reviewing a finished file.
Batch by test coverage, not by turn Let the agent run unattended across a whole package wherever source tests exist to port alongside the code. The ported suite is the drift detector, and unlike a reviewer it does not get tired. A port of any real size is only finishable that way. Reserve single-file, attended porting for code with no test coverage — there your reading is the only check there is. Coverage is what buys the autonomy, so the eligibility rule is mechanical rather than a judgement call the agent makes in its own favour.
Demand the deviation list Ask for the code and an explicit list of every place the target differs from the source and why. A deviation the agent will not name is a deviation you find at runtime.
Forbid improvement by name A general instruction to be faithful loses to a specific opportunity to be clever. Enumerate the clever things instead — redesign, rename, extract a helper, deduplicate, optimize, cache, memoize, swap a data structure, go async, add a null check, add a log line, add a type annotation, modernize syntax, fix a source bug, delete dead code. Rule 6 of the contract is long on purpose: every line of it is something an agent will otherwise do and defend as obviously better, and every one costs a reader the recognition the port exists to preserve.
Make review asynchronous Commit once per package, put the short hash and a source-against-target diff link on every scorecard row, and have the agent hand back deep links into the report. Review then happens on your schedule and at the granularity you pick, without standing between the agent and the next file. The batch is the unit of review, not the turn.
Give uncertainty somewhere to go Inviting the agent to say "I did not understand this" only works if saying it is cheap and does not halt the run. Give it a marker to leave at the site — PORT-QUESTION: file:line — … — and gather every marker into a band at the top of the scorecard. The agent keeps moving and the doubt lands on your desk, instead of being quietly resolved by a guess that reads exactly like the rest of the port.
Never let it grade itself from memory A status of ported means the tests ran in this session and passed. Require the run, require the pasted output. An agent asked whether its own work is complete will say yes.
Make completion a checklist, not a feeling An empty work queue is not a finished port. Define done as a numbered list of verifiable claims — every source file has a row, the full target suite matches the frozen baseline test-for-test, zero open questions, the drift sweep clean — and make the agent report PASS or FAIL against each with the command it ran. Otherwise "done" means "I have run out of obvious work", which is a different thing and arrives much earlier.
Put the stop in the prompt For escalations, end with "Then stop and wait. I will pick." An agent that has been asked to research options and has not been told to stop will research the options and then implement one.
Placeholders

The step prompts use square-bracket placeholders — [SOURCE_ROOT], [TARGET_ROOT], [RELATIVE_PATH], [SOURCE_PACKAGE], [SOURCE_API], [PROGRESS_REPORT_PATH], [DIFF_URL_PATTERN] and the rest. You do not fill these in. START establishes every one of them in its setup pass, from the tree or from its own defaults, and the agent resolves them from there. They are brackets on this page only so the prompts read as templates. If you send a step prompt by hand mid-port, paste it as it is — the agent already knows the values.

§5The Three Prompts
Everything you ever type

Three prompts, for the whole life of a port. START sets the port up and runs until something needs you. CONTINUE resumes, and tells you when there is nothing left to port. FINISH audits the result and, only if it passes, closes the port out. There is no fourth.

If the pasting gets tedious after a port or two, save the three as slash commands or snippets. Nothing depends on it.

START Use the Copy button Start the port — one paste, then it runs 
Run a port of this project to another language or platform, to
completion. Work autonomously. I will come back to say "continue" or to
answer a question; I am not reviewing each file as it lands.

SETUP — do only what is not already done. Work out everything you can
from the tree in front of you, state each decision, and ask me only what
you genuinely cannot determine. Mark every line (detected), (default)
or (yours).

 1. SOURCE. Read the working directory. Determine the source language
    and platform from its build files, manifests, lockfiles and file
    extensions. State what you found and continue. Ask me ONLY if the
    tree holds more than one plausible language or target platform and
    you cannot tell which is the subject of the port. The source root is
    where you are, unless the layout clearly says otherwise.

 2. TARGET. Ask me one question: what language and platform are we
    porting to? This is the only thing that cannot be read off disk.
    Ask it plainly and wait.

 3. TARGET ROOT. Propose a sibling directory alongside the source root,
    so the two trees sit at the same level and a source path maps to a
    target path by swapping the root. State the path. Use it unless I
    object.

 4. DIFF. Find a way to show one source file against one target file,
    trying in this order: a forge compare URL, if this repo has a remote
    that supports one; else `git difftool`; else `diff -u`. Test the one
    you pick on two real files before adopting it. State which you will
    use, and that you will keep using it unless I say otherwise.

 5. TESTS. Find the source test runner and the command that runs its
    full suite. Run it now and paste the summary line. If you cannot run
    it, stop and tell me — everything downstream compares two real test
    runs, and a port where you cannot execute tests is not one to run
    unattended.

 6. CONTRACT. Check whether the PORT CONTRACT is already installed for
    this repository. If it is, say so and skip. If not, install it from
    the appendix at the end of this command:
      - if this repository exists for the port, put it in the repo-root
        instructions file;
      - if the port is one workstream inside a repository used for other
        things, install it as a path-scoped rule covering only the two
        trees.
    Ask me which, in one question, only if the repository itself does
    not tell you. Never install it user-level or machine-wide — it is
    long, it is resident, and it is wrong everywhere but here.

 7. STEPS. Write the step prompts from the appendix to PORT-PROMPTS.md
    at the target repo root, unless that file already exists. Read them
    from there whenever the loop names one; do not work from your memory
    of what a step id means.

 8. REPORT. Choose the progress report path — beside the target tree,
    inside the repo, committed — and state it.

 9. QUESTION CAP. You will pause when open questions reach 10, unless I
    give you another number. State it as a default.

Report those nine as nine lines, then carry straight on. Do not wait for
approval except where you had to ask.

SURVEY — then, without stopping:

  INVENTORY      list every source file with its types, its dependencies
                 and whether a source test covers it, ordered so that
                 leaf modules come first.
  BASELINE       run the source test suite as it stands today and freeze
                 the result per file; classify every file GREEN, RED or
                 NONE.
  MIRROR         create the target tree as an empty mirror of the
                 source: one directory per source directory, one empty
                 file per source file, no code in any of them yet.
  REPORT-CREATE  create the progress report: every source file present
                 as a row, its baseline recorded, status NOT STARTED.

Report the three counts and the first five packages in order, then begin
porting. Do not wait for my approval to start.

LOOP — repeat until the queue holds no GREEN files:

  a. Take the next package in dependency order with GREEN files left.

  b. BATCH — batch-port its eligible files, each tested against its
     baseline, each row updated as it lands.

  c. COMMIT — commit the batch; write hashes, diff links and paired test
     results onto every row; add new questions to the band.

  d. REPORT-UPDATE — update the scorecard: statuses, dates, recomputed
     directory scores, summary band.

  e. Every fifth package, REPORT-AUDIT — audit the report against disk
     and apply the corrections. Do not skip this because things look
     fine; an unattended run drifts optimistic and this is what catches
     it.

  f. LINKS — print deep links: the package node, plus any row that needs
     my eyes, in priority order.

  g. Continue to the next package. Do not wait for me.

STOP AND WAIT only when:
  - a stop condition inside BATCH fires;
  - a missing API needs the ESCALATE decision;
  - open questions reach the cap, or one question blocks a whole
    package. When you pause for questions, present them as QUESTIONS says:
    grouped by the underlying uncertainty they share, ordered by blast
    radius, each with its source quoted and the reading you ported
    against. Do not make me go and find them;
  - the queue holds nothing but RED and NONE files — those are the
    attended lane and we do them together.

When you pause, give me one line each: what you finished, why you
stopped, what you need from me, and the deep link to look at. Then stop
cleanly. Do not half-start the next package.

When the queue empties, do not tell me the port is done. Run FINISH.
Use the Copy button, not a text selection. Copy takes every other prompt on this page with it — the contract, CONTINUE, FINISH and all fifteen step prompts — which is why one paste is the entire setup. Select the box by hand and you get this prompt alone: the agent would start the port with no contract and no step prompts, and nothing would tell you it had. The question cap defaults to ten. Without one the agent runs to the end of the tree before asking, and a single enormous batch of questions is a worse conversation than several small ones.
CONTINUE Use the Copy button Continue — or say what is left 
Continue the port in this repository.

Anything named in capitals in this prompt — INVENTORY, BATCH, QUESTIONS and the
rest — is a step prompt stored in PORT-PROMPTS.md at the repo root. Read the one you need from that file. Do not work
from your memory of what an id means, and do not improvise a step you cannot find.
The loop itself is in PORT-PROMPTS.md too, under START; its stop
conditions and its step order are what you are resuming.

Re-anchor first, briefly:
  - The PORT CONTRACT is installed for this repository — in its instructions file
    (CLAUDE.md or AGENTS.md) or as a rule under .claude/rules/. It should already be
    in your context. If it is not, find and read it. If you cannot find it at all,
    stop and tell me — do not reconstruct it from memory and do not proceed without
    it.
  - Read [PROGRESS_REPORT_PATH]. Its path is recorded in
    PORT-PROMPTS.md if you do not have it.
  - Give me three lines: totals by status, what you were doing when you
    stopped, and what is next.

Apply anything I answered earlier in this conversation before you
restart the loop. If you stopped on a question I have now answered,
close it per QUESTIONS: apply the answer, delete the marker, leave a
PORT-DEVIATION if the answer moved the target off a literal reading of
the source, re-run the affected tests against their baselines, and
update the scorecard.

Then resume the START loop from step (a) and keep going under the same
stop conditions.

IF THERE IS NOTHING LEFT TO PORT — no GREEN files in the queue — do not
start anything and do not declare the port finished. Tell me, in four
lines:
  - the totals by status;
  - what remains in the attended lane (files with no source test
    coverage, or whose source tests were already red at baseline), which
    we do together one at a time;
  - anything still BLOCKED, and on what;
  - that I should run FINISH next.
Then stop.
The re-anchor matters more than it looks. A resumed session carries none of the prior context, so every fidelity rule has to be re-established before the agent touches a file — the same decay the contract exists to counter.
FINISH Use the Copy button Audit, and close the port out 
Run the full completion audit for the port in this repository.

Anything named in capitals in this prompt — INVENTORY, BATCH, QUESTIONS and the
rest — is a step prompt stored in PORT-PROMPTS.md at the repo root. Read the one you need from that file. Do not work
from your memory of what an id means, and do not improvise a step you cannot find.

The port is not done because the queue is empty. It is done when every
numbered check in this prompt is true and you have shown me what you
ran. Verify them in
order. Report each as PASS or FAIL with the command and its output. Fix
nothing while auditing.

COVERAGE
  1. Every file under [SOURCE_ROOT] has a row in
     [PROGRESS_REPORT_PATH]. Count both. The numbers match.
  2. Every row resolves to a target file that exists on disk.

STATUS
  3. Every row is PORTED, or BLOCKED with a named decision and owner,
     or marked out of scope with my agreement recorded on the row.
  4. No row sits at IN PROGRESS or NOT STARTED.

TESTS — the expensive check; do not shortcut it
  5. Run the FULL target suite now, in this session. Not per file, not
     from memory, not from the last commit's recorded output.
  6. Compare that whole run against the frozen baseline recorded in the
     progress report (written once by the BASELINE step, never edited since),
     test-for-test: every baseline test name is present in the target,
     and passes if and only if it passed at baseline.
  7. List every divergence in either direction. A target test passing
     where the baseline failed is a divergence needing an explanation,
     not a celebration — it means behaviour changed.
  8. Confirm the baseline column is byte-identical to what the baseline
     step originally wrote.

QUESTIONS AND DEVIATIONS
  9. Zero open PORT-QUESTION markers anywhere in [TARGET_ROOT]. Grep
     the tree for them; do not trust the band.
 10. Every PORT-DEVIATION in the code appears in a commit body and on
     its scorecard row, and none of them is news to me.

FIDELITY
 11. Run DRIFT, the drift sweep — its text is in PORT-PROMPTS.md — across
     the whole tree. Structure, names, shape, invention and silent
     deviation all come back clean.
 12. Every file in compat/ has its documentation block and its tests,
     and those tests pass.

TRAIL
 13. Every row's commit hash resolves and every DIFF link opens.
 14. Every directory score equals the count of its rows, and the
     summary band equals the tree.
 15. The PORT LOG accounts for the whole port: every commit in the
     target history has an entry, the sequence has no gaps, no entry
     has been edited since it was written, and reading the log top to
     bottom reconstructs how the tree reached its current state.

Finish with one verdict line: COMPLETE, or NOT COMPLETE followed by the
numbered checks that failed, each with a deep link. If anything failed,
do not quietly fix it — list it and wait for me. I will decide what to
do and send you back round with CONTINUE.

THEN, AND ONLY ON COMPLETE — finalize the port:

  a. Commit anything uncommitted, and append the closing PORT LOG entry:
     the verdict, the date, the final totals.
  b. Retire the PORT CONTRACT. Remove it from the instructions file or
     rule where you installed it, and show me the diff. Its prohibitions
     are exactly wrong for the maintenance that follows — from here we
     DO want the target refactored, optimised and made idiomatic, and
     leaving the contract in place would forbid all of it.
  c. Leave PORT-PROMPTS.md and the progress report in the repo. The
     report and its log are the record of how this code got here.
  d. Leave the three commands installed. The next port reuses them.
  e. Tell me in three lines what was ported, what remains in the
     attended lane if anything, and where the report lives.
Checks 5 and 6 are the ones an agent will want to answer from the scorecard it wrote itself. Make it run the suite. The scorecard records past claims; the audit is the only place those claims meet the tree as it stands today.

§6The Port Contract
CONTRACT

The rules the agent works under. START installs it for you; open it to read what you are committing the port to.

You never paste this one yourself. Copying START copies it too, as Appendix A, and the agent installs it into the port repository on its first run — after which it loads automatically in every later session, which is what keeps CONTINUE and FINISH short. It is printed here because it is the substance of the whole method, rule 6 in particular, and you should read what you are committing the port to.

CONTRACT In the START copy Port contract — installed by START, never pasted 
PORT CONTRACT — read this before you touch a file.

SOURCE (original, authoritative): [SOURCE_LANG] / [SOURCE_PLATFORM] at [SOURCE_ROOT]
TARGET (new, under construction): [TARGET_LANG] / [TARGET_PLATFORM] at [TARGET_ROOT]

Standing rules, in priority order:

1. The source is the specification. Where the source and your judgement
   disagree, the source wins. Port what is there, not what you would
   have written.

2. Keep the target core code as close to line-for-line identical to the
   source as the target language permits. A programmer who knows the
   source must be able to open the target file and recognise it.
   Preserve declaration order, statement order, branch order, early
   returns, and the shape of every loop.

3. Mirror every name. Directory names, file names, class names, method
   names, property names, constants, enum cases and test names carry
   over unchanged, except where target-language casing convention forces
   a change — and then only the casing changes, never the word.

4. Mirror the tree. [TARGET_ROOT] sits alongside [SOURCE_ROOT] so the
   two trees read side by side. Every source directory gets a target
   directory at the same relative path.

5. Port the tests. Any source test that validates behaviour you are
   porting gets ported together with the code it covers, in the same
   run.

6. Do not improve the code. Specifically, and not as a general
   sentiment — do not:
     - redesign, re-architect, or substitute a different pattern
     - rename anything "for clarity"
     - collapse, split, merge or reorder classes, methods or fields
     - extract a helper, or deduplicate code the source repeats
     - introduce a library, framework or build tool the source does not
       use
     - improve, replace or "simplify" an algorithm
     - optimize — no caching, memoization, lazy evaluation,
       precomputation, pooling, batching or added parallelism that the
       source does not already have
     - tighten a loop, or swap an explicit source loop for a target
       idiom (map / filter / reduce / comprehension), or the reverse
     - change a data structure — a set for a list, a map for an array
     - change the concurrency model, or make a synchronous path async
     - add error handling, null checks, validation, retries or timeouts
       the source does not have
     - add logging, telemetry, metrics or assertions the source does not
       have
     - add type annotations, generics, immutability or visibility
       modifiers beyond what the target language needs to compile
     - extract magic numbers or strings into named constants
     - modernize syntax past what the target language requires
     - fix a source bug, remove dead code, or drop an unused variable
   Each of those is a real improvement, and each one costs a reader the
   recognition this port exists to preserve. Raise them with me. We do
   them later, on the target, as their own change.

7. Where the target language leaves you no choice but to deviate, leave
   a comment at the deviation site in exactly this form, and report it:
     PORT-DEVIATION: : — 

8. Where you do not understand the source, do not infer intent from the
   names and do not pick whichever reading is easiest to port. Leave a
   comment at the site in exactly this form, and keep going:
     PORT-QUESTION: : — 
   A PORT-QUESTION is not a failure and does not stop your run. An
   invented interpretation is a failure, and it reads exactly like the
   rest of the port.

9. Batch only where tests cover it. You may port many files in one
   unattended run when source tests exist for them and you port and run
   those tests as you go. A file with no source test coverage is ported
   one at a time, with me reading it.

Confirm you have read this, and restate rules 2, 3, 4 and 9 in your own
words, before you start.
The closing restatement is the point of it. An agent that paraphrases rules 2, 3, 4 and 9 correctly is anchored for the session; one that paraphrases them loosely tells you so before it has written any code. Rule 6 is deliberately a list rather than a principle — principles lose arguments with specific good ideas.
§7Survey, Mirror, Port
INVENTORY – COMMIT

The steps START runs to survey the source and port a package, printed in full.

START runs INVENTORY, BASELINE and MIRROR in that order, then works through the rest as the port needs them; FILE and FILE-TESTS it uses only in the attended lane. They are printed here so you can read what START is actually asking for. To run one again, name it — the agent has them all. Do the whole survey before any target code exists: the inventory sets the porting order, the baseline run establishes which source tests were green before anyone touched anything, and the flagged-API list tells you which conversations you owe the team.

Porting then runs in two lanes, and the inventory decides which lane each file goes in.

Lane Eligibility How it runs
Autonomous
Batch		 Source tests exist for the file and were green in the baseline run. BATCH ports whole packages unattended, running each ported test as it goes. COMMIT commits the batch and writes diff links onto every scorecard row. You review afterwards, from the links, at whatever depth you like.
Attended
One file		 No source test, or the source test was already red or skipped at baseline. FILE and FILE-TESTS, one file per turn, with you reading the result. Without a green baseline to match against there is no mechanical check, so your reading is the check.

The split is what makes a large port finishable. Most of a mature codebase lands in the autonomous lane, and the attended lane shrinks to the genuinely untested corners — which is also an honest map of where the source project's own risk already sat.

INVENTORY In the START copy Inventory the source 
Inventory [SOURCE_ROOT]. Write no target code in this turn.

Produce one table covering every source file, with:
  - its path relative to [SOURCE_ROOT]
  - the public types it declares (classes, interfaces, enums, structs)
  - the public methods and properties on each
  - its direct dependencies on other source files
  - any platform or library API it calls that has no obvious
    [TARGET_LANG] / [TARGET_PLATFORM] equivalent — flag these, and do
    not attempt to solve them yet
  - whether a source test covers it, and that test file's path

Sort the table by dependency depth, leaf modules first. That order is
our porting order for the rest of the project.

Then report three counts: total source files, flagged APIs with no
target equivalent, and source files with no test coverage. Report counts
you can derive from the files. Do not estimate effort or duration.
BASELINE In the START copy Establish the source test baseline 
Before we port anything, run the SOURCE test suite in the source project
and record what it does today. This is the baseline every target result
gets compared against.

  - Run the full source suite. Do not fix anything, do not skip
    anything, and do not adjust the source to make it greener.
  - Record per source test file: tests passed, failed, skipped, and the
    individual test names in each bucket.
  - Record the date of the run and the source revision it ran against.

Then classify every source file from the inventory:
  GREEN    covered by source tests that all pass — eligible for the
           autonomous batch lane
  RED      covered by source tests that fail or are skipped today —
           attended lane only, and tell me: we are porting behaviour
           nobody currently verifies
  NONE     no source test coverage at all — attended lane only

Write the baseline into [PROGRESS_REPORT_PATH] as a fixed column beside
each row. It does not change as we port; it is the yardstick.

Report the three counts, and list every RED file with its failing test
names. A source suite that is not green before the port starts is worth
knowing about now rather than discovering through a ported test we
assume we broke.
This prompt is what makes a Ported claim provable. Without a baseline, a red target test is ambiguous — the port may be wrong, or the behaviour may have been broken in the source all along. With one, the target is measured against the source test-for-test rather than against green.
MIRROR In the START copy Mirror the source tree, empty 
Create the target tree at [TARGET_ROOT], mirroring [SOURCE_ROOT].

[TARGET_ROOT] sits at a level where the two trees can be browsed side by
side — same relative paths under each root, so that a source path maps
to a target path by swapping the root and the file extension.

  - One target directory per source directory, same relative path, same
    directory name.
  - One empty target file per source file, same base name, target
    extension.
  - Mirror the source's test tree the same way.
  - Add the minimum build or project manifest [TARGET_PLATFORM] needs to
    compile an empty tree, and nothing else.

Write no implementation in this turn. When you are done, print the two
trees side by side and list every source path you could not mirror,
with the reason.
FILE In the START copy Port one source file — the attended lane 
Port [SOURCE_ROOT]/[RELATIVE_PATH] to [TARGET_ROOT]/[RELATIVE_PATH].

First, read the source file in full and list every type, method and
property you are about to create in the target. If that list does not
match the source one-for-one, say so and wait for me.

Then port it under the PORT CONTRACT — installed for this repository in
its instructions file or under .claude/rules/, and it should already be
in your context. If it is not, stop and say so.

  - same order of declarations as the source
  - same method bodies, statement for statement, wherever the target
    language allows it
  - same names, adjusted only for target casing convention
  - source comments carried over verbatim; add a new comment only to
    explain a forced deviation
  - imports resolved against the already-ported target tree, never
    against a new third-party dependency

When you finish, report:
  1. Every place the target necessarily differs from the source, each
     with the source line number and the reason.
  2. Every source API you had to substitute, and what you substituted.
  3. Anything in the source you did not understand. Say so plainly —
     do not guess and do not fill the gap from the names.

Touch no file other than the target file for this module.
FILE-TESTS In the START copy Port that file’s tests 
Port the source tests covering [SOURCE_ROOT]/[RELATIVE_PATH].

  - Mirror the test file's path and name into the target test tree.
  - One target test per source test, same test name, same assertions in
    the same order.
  - Keep fixture data byte-identical. Where the source reads a fixture
    file, copy the file across rather than retyping its values.
  - Add no test the source does not have.
  - Drop no source test for being awkward. A test you cannot port stays
    in the target as a skipped test whose skip message names the source
    test and the blocker.

Run the ported tests and report pass, fail and skip counts, with the
failure output pasted verbatim for anything red.

A red test means the port is wrong until proven otherwise. Do not make a
test pass by weakening its assertion, relaxing a tolerance, or editing a
fixture. Bring me the failure instead.

The autonomous lane

BATCH and COMMIT are the pair that carries a large port. BATCH runs unattended across a package; COMMIT closes it with a commit and writes the review trail into the scorecard so you can audit the run afterwards instead of supervising it.

BATCH In the START copy Batch-port a covered package — unattended 
Batch-port [SOURCE_PACKAGE]. Work autonomously — do not check in with me
between files.

ELIGIBILITY. A file enters this batch only if the baseline marked it
GREEN: source tests exist for it and they passed at baseline. Files
marked RED or NONE stay NOT STARTED; list them at the end and we will
take them in the attended lane. Do not talk yourself past this rule
because a file "looks simple".

For each eligible file, in dependency order:

  1. Port the source file under the PORT CONTRACT — the one installed
     for this repository, in its instructions file or under
     .claude/rules/. Rule 6 applies unchanged, and applies harder
     without me watching: same declaration order, same statement order,
     same names, same shape, comments carried over, no improvement of
     any kind on that list. If the contract is not in your context,
     stop and say so rather than working from memory of it.
  2. Port its source tests under the same rules — same test names, same
     assertions in the same order, byte-identical fixtures. The full
     text of the per-file steps is in PORT-PROMPTS.md under FILE and FILE-TESTS.
  3. Run those tests and compare against the baseline for that file. The
     bar is not "green", it is "matches the baseline test-for-test":
     same test names present, same ones passing.
  4. On a match, record PORTED on that row in [PROGRESS_REPORT_PATH]
     immediately — as you go, not at the end of the batch. A run that
     dies mid-package must leave an accurate report behind it.
  5. On a mismatch, attempt a fix twice. If it still does not match,
     revert that file pair, record IN PROGRESS with the failure output
     and the baseline it failed to match, and continue. One stubborn
     file must not stall the batch.
  6. Where you do not understand something, leave a PORT-QUESTION at the
     site per contract rule 8 and keep going. Do not stop the run for a
     question and do not resolve one by guessing.

STOP THE BATCH EARLY and come back to me only if:
  - you hit a source API with no target equivalent — that is SHIM or ESCALATE
    in PORT-PROMPTS.md, depending on how large it is;
  - more than a quarter of the batch fails to match baseline, which
    means the contract or the mirrored tree is wrong rather than the
    files;
  - you find yourself wanting to change a source behaviour;
  - a file outside [SOURCE_PACKAGE] needs editing to make this one work.

When the batch ends, report per file: ported / in progress / skipped as
ineligible, the baseline-versus-target test comparison, every
PORT-DEVIATION you left, and every PORT-QUESTION you left.

Then, without waiting for me: run COMMIT to commit the batch and write the
review trail, run REPORT-UPDATE to recompute the scorecard, and move to the next
package. Both are in PORT-PROMPTS.md. You own the bookkeeping — I should never have to ask you to
update the report.
COMMIT In the START copy Commit the batch and write the review trail 
Commit the batch just finished and leave me a trail I can review
asynchronously.

COMMIT
  - One commit per package, not one per file. Subject:
    "port([SOURCE_PACKAGE]):  files,  tests"
  - Body lists each ported file as " -> ", and
    beneath it every PORT-DEVIATION and PORT-QUESTION left in that file,
    one per line, each with its source file and line.
  - Do not commit a file whose ported tests do not match baseline. Those
    stay in the working tree at IN PROGRESS.
  - No prose in the commit about how the porting went.

SCORECARD — update [PROGRESS_REPORT_PATH] so every row in this batch
carries:
  - the short commit hash, linked to the commit
  - a DIFF link that opens the source file against the target file at
    that commit, built from [DIFF_URL_PATTERN]
  - the baseline result and the target result side by side
  - today's date
  - any PORT-QUESTION left in that file, linked to the line

Recompute every ancestor directory score from its rows. Add the new
questions to the open-questions band at the top of the report, and
append one entry to the PORT LOG at the bottom: the prompt that ran, the
package, the file and test counts, the commit hash, and the deep link to
the package node.

HAND BACK
  - the commit hash and the file count
  - the deep link to the scorecard node for [SOURCE_PACKAGE]
  - a deep link per row that needs my eyes, each labelled with why

Then continue to the next package without waiting, unless something in
the stop list fired.
The commit is the unit of review, which is what lets the agent keep running. Reviewing a package-sized diff against a scorecard row that already tells you the tests match baseline is a different job from reading every file as it lands — and it is a job you can do tomorrow.
§8When the Target Has No Parallel
SHIM · ESCALATE

What happens when a source API has no counterpart: build a small replacement, or stop and ask you.

Some source API will have no counterpart on the target platform. The decision that matters is simple or complicated, and it is the one decision an agent reliably gets wrong in its own favour — reimplementing a subsystem is more fun than asking. Make the size judgement an explicit first step, and give the agent a hard exit into ESCALATE.

SHIM In the START copy Missing API, simple — build it, document it, test it 
[SOURCE_API] has no equivalent on [TARGET_PLATFORM].

Judge the scope first, and judge it against me rather than against your
appetite: is this a small, self-contained, fully understood piece of
behaviour you can reproduce faithfully — or is it a subsystem? If there
is any doubt, treat it as a subsystem, stop, and tell me we need the
escalation path instead.

If it is genuinely small, build it:

  - Put it at [TARGET_ROOT]/compat/[SOURCE_API_NAME].[ext] — one
    directory reserved for replacements of source-platform APIs.
  - Name the file and the type after the source API, not after what it
    does internally, so a search for the source name finds it.
  - Match the source API's signature, argument order, return type, error
    behaviour and edge-case behaviour — including behaviour you think is
    wrong. Fidelity here, not correctness.
  - Document it at the top of the file, at length:
      * the source API it replaces, fully qualified
      * a link to the source platform's documentation for that API
      * why [TARGET_PLATFORM] has no equivalent
      * every behaviour you matched deliberately, especially the
        surprising ones, with the source doc or source line that shows it
      * every behaviour you knowingly did not match, and the consequence
        for the call sites
  - Write tests for it at the mirrored path in the target test tree,
    covering the documented behaviour and the edge cases — including the
    surprising ones. These tests are the record of what we promised.

Then report the new file, its test file, the tests' pass/fail output,
and the behaviours you could not match.
ESCALATE In the START copy Missing API, complicated — research, recommend, stop 
[SOURCE_API] has no equivalent on [TARGET_PLATFORM] and is too large to
reimplement safely.

Do not write a replacement. Do not begin porting anything that depends
on it. Bring me a decision instead:

1. Describe exactly what the source uses this API for — which call
   sites, which behaviours, which guarantees. Cite source file and line
   for each one.

2. Find credible [TARGET_PLATFORM] libraries that cover it. For each:
   name, maintainer, licence, latest release date, and the link you
   found it at. Say plainly which of the behaviours in (1) it covers and
   which it does not. Do not list a library you have not confirmed
   exists at a real URL.

3. Give your recommendation, and the single thing about it that most
   worries you.

4. State the cost of the alternative — building it ourselves — as the
   list of source behaviours we would have to reproduce and test.

Then stop and wait. I will pick.
Record the outcome of that conversation somewhere durable — the chosen library, the date, and the behaviours it does not cover. The scorecard's Blocked row is the natural home for it until the decision lands.
§9The Progress Scorecard
REPORT-CREATE – LINKS

The report the agent keeps — status vocabulary, the mirrored tree, and the append-only port log.

One report, updated as work lands, audited against disk on a schedule. It mirrors the source tree as a collapsible hierarchy so that a directory node answers "how far through this package are we?" and a leaf row answers "is this file done, and how do we know?" In an autonomous port it is also the review surface: commit hashes, diff links and open questions all land on the row they belong to, so the scorecard is where you go rather than the terminal scrollback.

The report has two halves that answer different questions. The tree at the top says what is true now. The port log at the bottom says how it got that way — every step in the order it ran, append-only, corrections recorded as new entries rather than edits. The log is what turns a status into a record: a row marked Ported that nobody can trace back to the run that set it is a claim.

Status vocabulary

Status Means Evidence required to claim it
Ported Target file exists and its ported tests match the source baseline test-for-test. The baseline result for that file, and a target test run from this session, side by side: same test names present, same ones passing. Not "green" — equal. A source test that was already red at baseline may be red in the target too, and that still matches.
In Progress Target file exists; incomplete, or its tests diverge from the baseline. Which test names diverge, in which direction, with the failure output.
Shimmed Target depends on a hand-built replacement for a missing source API. A link to the compat file, and the list of behaviours it does not match.
Blocked Waiting on a decision or a missing library. The decision it waits on, named, and who owes it.
Not Started Target file is empty or absent. None. This is the default, and no row may sit outside the five.

Shape of the hierarchy

Directory nodes collapse; leaf rows carry the status. Each directory shows its rolled-up score — ported files over total files — counted from its children, never carried forward from a previous update. Every row carries the paired test result (baseline, then target), the commit it landed in, a diff link, and any open question left in that file. Every node and row has a stable id derived from its source path, so the agent can hand you [PROGRESS_REPORT_PATH]#net-HttpClient and you land on the row with its ancestors expanded. Structure only below; fill it from the real tree.

OPEN QUESTIONS — gathered from every PORT-QUESTION in the tree, newest first
net/RequestQueue.[ext]:118 — retry counter resets on 5xx but not on timeout; deliberate? source · target
render/FrameBuffer.[ext]:64 — two allocation paths, second appears unreachable source · target
[TARGET_ROOT]/   —/— ported
net/   —/— ported
HttpClient base — · tgt — Ported a1b2c3d · diff
RequestQueue base — · tgt — In Progress uncommitted · 1 question
SocketFactory base — · tgt — Shimmed a1b2c3d · diff · compat
render/   —/— ported
FrameBuffer base — · tgt — Blocked 1 question
ShaderCache no source test Not Started attended lane

Shape of the port log

The report's final section, and the thing the scorecard cannot be audited without. It runs oldest first, one entry per step, and it is append-only: a later correction is a new entry naming the one it supersedes, never an edit to the entry above. Structure only below.

Port log — in order, oldest first, append-only
0001—BASELINE whole tree · baseline frozen: — green, — red, — no coverage
0002—MIRROR whole tree · empty target tree created, — directories, — files
0003—BATCH net/ · — files ported, — matched baseline, — deferred node
0004—COMMIT net/ · committed a1b2c3d, — rows updated, — questions raised commit · node
0005—START paused · open-questions band reached the cap
0006—QUESTIONS net/ · — questions closed, — became deviations node
0007—REPORT-AUDIT audit · net/RequestQueue demoted Ported → In Progress — supersedes 0004 node
REPORT-CREATE In the START copy Create the progress report 
Create the port progress report at [PROGRESS_REPORT_PATH] — a single
self-contained HTML file, no build step, no external dependencies.

It is a scorecard over the mirrored tree:

  - A collapsible directory/file hierarchy mirroring [SOURCE_ROOT]
    exactly. Every source directory is a collapsible node; every source
    file is a leaf row.
  - Each leaf row carries: source path, target path, status, the
    BASELINE test result for that file (fixed, from BASELINE), the TARGET test
    result (current), the short commit hash it landed in linked to the
    commit, a DIFF link built from [DIFF_URL_PATTERN] that opens source
    against target at that commit, a last-touched date, and any open
    PORT-QUESTION left in that file linked to the line.
  - Each directory node carries a rolled-up score from its children —
    ported files over total files, plus the percentage.
  - A summary band at the top with the whole-tree totals and a count per
    status.
  - An OPEN QUESTIONS band directly beneath the summary, gathering every
    PORT-QUESTION in the tree: the question text, its source file and
    line, and links to both the source site and the target site. This
    band is the first thing on the page after the totals — questions are
    the part of the run that needs a human, so they do not get buried in
    a collapsed node.
  - Every directory node and every leaf row carries a stable id derived
    from its source path, with separators and dots replaced by hyphens,
    so [PROGRESS_REPORT_PATH]# deep-links to it. On load, read
    location.hash and expand the whole ancestor chain down to the target
    row, then scroll it into view. A link I saved last week must still
    resolve after the report is regenerated.

Status vocabulary, and nothing outside it:
  PORTED       target exists and its tests match the BASELINE result for
               that file test-for-test — same test names present, same
               ones passing. The bar is equality with the baseline, not
               greenness.
  IN PROGRESS  target exists; incomplete, or its tests diverge from the
               baseline
  SHIMMED      target depends on a hand-built replacement for a missing
               source API — link the compat file from the row
  BLOCKED      waiting on a decision or a missing library — name it
  NOT STARTED  target file is empty or absent

Derive every row from the files actually on disk and from real test
runs. Do not invent a status, do not write a percentage you did not
count, do not mark a row PORTED without both results to compare, and do
not add a projected completion date.

Give directories that are fully ported a collapsed default state and
everything else an expanded one, so the report opens on the work that
is left.

PORT LOG — a final section at the BOTTOM of the report: the steps of
this port in the order they happened, oldest first. One entry per step,
each carrying:

  - a sequence number
  - the date and time it ran
  - which prompt ran — BASELINE, BATCH, COMMIT, REPORT-AUDIT, QUESTIONS, FINISH and so on
  - what it acted on: the package, the file, or "whole tree"
  - the outcome in one line, with counts
  - the commit hash where there is one, linked
  - a deep link to the scorecard node the step affected

Log every step, not only the successful ones: the baseline run, each
batch, each commit, each audit and what it corrected, each pause and
why, each question answered, each drift sweep, each completion audit
and its verdict. The prompt ids in a log entry are labels for the reader
— the prompts themselves live in PORT-PROMPTS.md at the repo root.

The log is APPEND-ONLY. Never rewrite an entry, never reorder, never
delete, and never replace a run of entries with a summary. When a later
step corrects an earlier claim — an audit demoting a row from PORTED,
say — that is a NEW entry recording the correction and naming the entry
number it supersedes. The superseded entry stays exactly as written.

Scorecard and log answer different questions. The scorecard says what
is true now; the log says how it got that way, in order. The second is
what makes the first auditable, because a status nobody can trace back
to the run that set it is a claim rather than a record.

Render the log collapsed by default with the most recent ten entries
shown, and a control to expand the whole history.
REPORT-AUDIT In the START copy Audit the progress report against disk 
Audit [PROGRESS_REPORT_PATH] against the trees on disk. Change nothing
in this turn — report first.

For every row in the report, check:
  - Does the target file exist at the path claimed?
  - Does the source file still exist at the path claimed?
  - Does the declared status match reality? Run the ported tests for
    that file and compare against the row's baseline to settle PORTED
    against IN PROGRESS. Do not accept a green status on trust,
    including your own from an earlier session.
  - Is the BASELINE column unchanged since the baseline step first wrote
    it? It is a fixed yardstick.
    If anything has edited it, that is a finding — report it loudly.
  - Does the commit hash on the row exist, and does the DIFF link
    resolve?
  - Does each SHIMMED row still link to a compat file that exists?
  - Is each BLOCKED row still blocked, or was the decision made?
  - Does every PORT-QUESTION still in the target code appear in the
    open-questions band, and does every question in the band still exist
    in the code?

Then walk [SOURCE_ROOT] and find every source file with no row in the
report at all.

Output four lists:
  1. Rows whose status is wrong, each with the true status and the
     evidence.
  2. Rows pointing at files that no longer exist.
  3. Source files missing from the scorecard entirely.
  4. Directory scores that do not equal the count of their children.
  5. Baseline values that have been altered since they were first
     written.
  6. Questions in the code but not in the band, or in the band but no
     longer in the code.
  7. Steps visible in the git history with no corresponding PORT LOG
     entry, and log entries whose commit hash does not exist.

Check the log itself for tampering: entries out of sequence, gaps in the
numbering, or an entry whose wording has changed since it was written.
An append-only log that has been edited is worth less than no log.

When I tell you to apply the corrections, append one PORT LOG entry per
correction, each naming the entry number it supersedes.

Finish with the corrected totals. Then wait — I will tell you whether to
apply them.
REPORT-UPDATE In the START copy Update the progress report after work lands 
Update [PROGRESS_REPORT_PATH] for the work just completed.

  - Set the status of every file touched in this session, using only the
    five status values, and only what you can evidence. PORTED requires
    that you ran the ported tests in this session and the result matches
    that row's baseline test-for-test.
  - Write the target test result alongside the untouched baseline. Never
    edit a baseline value.
  - Write the short commit hash and the DIFF link onto every row that
    landed in a commit.
  - Add any new PORT-QUESTION to the row and to the open-questions band;
    remove from the band any question whose marker is gone from the code.
  - Append one PORT LOG entry for this update: what ran, what it acted
    on, the counts, and the deep link. Append only — leave every earlier
    entry exactly as it stands.
  - Set the last-touched date on those rows to today's date.
  - Recompute the rolled-up score on every ancestor directory node and
    on the summary band. Count them from the rows; do not carry a
    previous number forward.
  - Add rows for anything new: a compat file you built, a test file you
    created.
  - For any row moved to BLOCKED, name the decision it now waits on.

Change nothing else. No restructuring, no re-styling, no reordering, and
no note in the document about the update itself — the report shows the
current state, not its own history.

Report the before and after totals for each status.
Run REPORT-UPDATE at the end of every porting session and REPORT-AUDIT every fifth package, as the loop does. The audit is the expensive one, and the one that catches a scorecard slowly drifting optimistic across an unattended run.
LINKS In the START copy Hand back deep links 
Give me deep links into [PROGRESS_REPORT_PATH] for the work you just
did. Print them here in the terminal; I will open them.

  - One link to the summary band.
  - One link to the open-questions band if you added anything to it.
  - One link per directory node you touched, anchored so the report
    opens with that node expanded.
  - One link per row that needs my eyes, each labelled with why in a few
    words: tests diverge from baseline, new shim, newly blocked, a
    deviation you were unsure about, a question you left.

Anchors are the stable ids derived from the source path. If a row you
need to link has no anchor, add the anchor to the report — do not
approximate with the nearest heading, and do not hand me a link to the
top of the page with instructions to scroll.

Order the links by what most needs attention first. Above them, one line
saying what I am looking at and what decision, if any, you need back
from me. Below them, say whether you are continuing or waiting.
This is what makes an unattended run reviewable rather than merely fast. The agent finishes a package, posts its links in priority order, and keeps going; you open the ones that matter when you next look at the terminal.
§10Open Questions and Deviations
QUESTIONS

The two inline markers that carry what the agent could not settle, and how they reach you.

Two inline markers carry everything the agent could not settle on its own. Both live at the site in the target code, both name the source file and line, and both get gathered into the scorecard. They are the mechanism that lets an agent keep running without papering over what it did not know.

Marker Means Where it surfaces
PORT-DEVIATION:
Decided		 The target necessarily differs from the source here, and the agent knows why. The commit body for its batch, and the row in the scorecard. Reviewed with the diff.
PORT-QUESTION:
Open		 The agent could not determine what the source intends, and declined to guess. The open-questions band at the top of the scorecard, linked to both the source line and the target line. Needs a human.

A question costs nothing to leave and does not stop the run. That is the point: the alternative is an agent resolving its own uncertainty silently, handing you a port where the guesses are indistinguishable from the translations. Sweep the band periodically and answer in batches.

QUESTIONS In the START copy Sweep and close open questions 
Gather every open PORT-QUESTION across [TARGET_ROOT] and bring them to
me as a batch. Answer none of them yourself.

For each question, give me:
  - the question as you wrote it
  - the source file and line, with the surrounding source quoted — a few
    lines either side, enough to judge it without opening the file
  - the target file and line where the marker sits
  - what you did in the meantime: the reading you ported against, and
    what changes if that reading is wrong
  - the blast radius: which other ported files depend on this answer

Group questions that turn on the same underlying uncertainty — one
answer often closes several — and order the groups by blast radius,
largest first.

Then stop and wait for my answers.

When I answer: apply each answer, delete the PORT-QUESTION marker, and
where the answer forced the target away from a literal reading of the
source, leave a PORT-DEVIATION in its place recording the decision and
that I made it. Re-run the affected tests against their baselines,
update the scorecard rows and the open-questions band, and give me the
deep links.
Grouping by shared uncertainty is what keeps this cheap: a package's questions usually turn out to be a handful of real ones about the source's intent, and answering those closes the rest.
§11Drift Sweep
DRIFT

The periodic check for familiarity eroding a file at a time.

Familiarity erodes a little at a time — a helper extracted here, a method renamed there, each defensible on its own. Sweep for it periodically against the whole tree rather than trusting per-file review to catch it.

DRIFT In the START copy Sweep the target for drift from the source 
Sweep [TARGET_ROOT] against [SOURCE_ROOT] for drift. Change nothing —
report only.

Find, in five categories:

1. STRUCTURE — any target directory with no source counterpart, and any
   source directory with no target counterpart.

2. NAMES — any class, method, property, constant, enum case or test
   whose target name differs from its source name by more than
   target-language casing convention.

3. SHAPE — any ported method whose declaration order, statement order,
   branch order or early-return structure differs from the source.

4. INVENTION — any target type, method, helper or third-party dependency
   with no source counterpart that is not a documented compat file.

5. SILENT DEVIATION — any place the target behaves differently from the
   source with no comment at the deviation site naming the source file
   and line.

For each finding give the source path and line, the target path and
line, and the category. Rank the findings by how much familiarity each
one costs a programmer who knows the source and is reading the target
for the first time.

Propose no fixes yet. I want the shape of the drift before the patch.
§12Corrections in Flight
What to say when it drifts

What to say when the agent drifts. Worth skimming once before your first port.
When the agent does this Say this
Renames something "for clarity" Restore the source name. Rule 3 of the contract is not a preference. If the source name is genuinely wrong, we rename it in the source first, then port the rename.
Extracts a helper the source does not have Inline it back. The source's duplication is part of what a reader recognises. Extraction is a refactor, and refactors happen after the port, on the target, as their own change.
Fixes a bug it noticed in the source Port the bug. Then tell me about it separately so we can fix it in the source and port the fix. A port that silently diverges in behaviour is worse than a port that carries a known bug.
Optimizes while porting — caches, memoizes, goes async Revert to the source's shape. Performance work needs a profile on the target platform, which does not exist yet, so the "optimization" is a guess that also destroys the line-for-line correspondence. It is rule 6, and it is the one most often defended as harmless.
Swaps a data structure for a better one Put the source's structure back. A list the source scans linearly stays a list. Complexity changes are behaviour changes at scale, and they are invisible in a diff that already looks like a translation.
Reaches for a framework the source does not use Drop the dependency and port the source's own implementation. New dependencies come through ESCALATE, with the research and the conversation.
Reports a file ported without running tests Run them and paste the output. Reset that row to IN PROGRESS until the result matches its baseline.
Batches a file with no source test Pull it out of the batch and revert it. Coverage is what licenses the batch; without a baseline to match against, nothing but your reading catches the drift. It goes in the attended lane with FILE and FILE-TESTS.
Debugs one failing file for twenty turns Two attempts, then revert the pair, mark it IN PROGRESS with the failure output, and continue the batch. A stalled run costs more than a deferred file, and the file reads better with fresh context later.
Marks a row PORTED because the target tests are green Green is not the bar; matching the baseline is. Re-check: if a source test was red or skipped at baseline and the target one passes, the port changed behaviour. That is a finding, not a win.
Edits a baseline value Restore it from BASELINE and treat everything that referenced it as unverified. The baseline is the yardstick; a yardstick that moves to fit the measurement measures nothing.
Resolves its own PORT-QUESTION Revert the resolution and restore the marker. A question the agent answers by re-reading the same source it already failed to understand is a guess with extra steps. Questions close through the QUESTIONS sweep, with a human in the loop.
Writes a shim for something large Revert it and send ESCALATE. The size judgement belongs to us, and it is easier to make before the code exists.
Declares the port done when the queue empties Paste FINISH. An empty queue means no more obvious work, which is not the same as a finished port — it says nothing about coverage, about the suite matching baseline, or about the questions still open in the tree.
Asks permission between packages Point at the START loop and say continue. Checking in on every package converts an autonomous run back into an attended one at the same cost, and the stop list already names every case that genuinely needs you.
Answers the completion audit from the scorecard Make it run the suite. The scorecard is a record of claims the agent made earlier; an audit that reads those claims back confirms only that it remembers writing them.
Fixes what the completion audit found, silently FINISH reports; it does not repair. A check that fails and is fixed inside the same pass never gets independently verified, and the next FINISH run inherits the assumption.
Narrates its progress inside the report Strip the commentary. The scorecard shows the current state; what changed belongs in the chat, not the document.
