Simulator Architecture Planning

Building the Dronscape Simulator

A tech-stack planning doc for a web + WebXR drone/swarm simulator where different AI and control models can be swapped in per experimental trial, with simulated RF channels and interference zones to see how each model responds to link degradation and jamming. This is a planning document, not an implementation — it lays out real, verified options and a recommended path, so a build plan can be scoped and approved separately.

How this connects to the taxonomy: the Dronscape feature landscape already catalogs the behaviors worth testing here — the Human/AI-Hybrid Control spectrum's Contested-Link Autonomy tier, and the Communications/C2 and Resilient-Comms categories (Anti-Jam RF Link, GPS-Denied Navigation, Self-Healing MANET, Bent-Pipe Relay). This simulator is the thing you'd build to actually exercise those behaviors against different control-model implementations, instead of just reading about them.
Verification note: every named tool/library below (ROS2 bridges, ArduPilot/PX4 SITL, Gazebo, NVIDIA Cosmos, MAVLink, ONNX Runtime Web, TensorFlow.js, NS-3, SPLAT!, Immersive Web SDK) was independently checked against its real repo/docs/release metadata — not recalled from memory. One earlier draft of this document got "Cosmos 3" wrong: it assumed the term could only mean an unrelated open-source command/telemetry tool with a similar name, and reported no such version existed. That was a mistake, not a real finding — it has been removed. NVIDIA Cosmos 3 is the real, drone-relevant thing the term refers to: an omni-modal physical-AI world-foundation-model platform released May 31, 2026. See §06 for the corrected verdict and "Sourcing & methodology" at the bottom for the trail. One other correction still stands: Meta's WebXR SDK lives at github.com/facebook/immersive-web-sdk, not under a meta-quest org path. And there remains no mature, widely-used web-native library for RF/jamming visualization — that layer has to be built custom.

01Requirements, restated

Four things the request is actually asking for, since a simulator built for one of these implicitly shapes what's possible for the others.

🕶️
Web + WebXR
Runs in a browser with no install; a headset (Quest, etc.) can drop into an immersive or AR view of the same simulation, not a separate build.
🔌
Pluggable control models
Different AI/autonomy/manual-control implementations can be inserted and selected per run, so trials actually compare something.
🧰
Reuse real stacks
ROS2 and ArduPilot are real, mature, and built for exactly this kind of software-only vehicle simulation; NVIDIA's Cosmos platform is a real option on the AI-model side specifically — worth weighing each against building from scratch.
📡
RF & interference simulation
Radio channels and jamming/interference zones a drone can fly into, so a control model's response to link loss or GPS denial is something you can actually observe, not just assert.

03Three tracks, in order of how much you reuse

These aren't mutually exclusive phases so much as a dial — Track 1 is fully self-contained and deployable as a static page like everything else in this repo; Track 2 and 3 trade that simplicity for real autopilot/model fidelity at the cost of needing a backend process somewhere.

The whole loop — physics tick, control model, RF-zone check, render — runs in one requestAnimationFrame loop, same pattern already used by other physics demos in this repo (see learning-gravity-sim/). A "control model" here is just an object with a fixed interface: given the current state and comms-quality reading, return a command. Swapping models is a dropdown, not a redeploy. This is also the only track where a genuinely novel AI control policy — a small trained network — can run in the browser itself via ONNX Runtime Web or TensorFlow.js, with zero backend, which is arguably the most "web-native" way to satisfy the pluggable-AI-model requirement.

Trade-off: the physics and autopilot behavior are only as realistic as what you write. Good for testing the logic of a control model's response to jamming; not a substitute for validating against real flight-control firmware.

ArduPilot and PX4 are both real flight-control firmware that runs as ordinary software with no hardware attached — that's what SITL is. Each has a real ROS2 bridge: ArduPilot's AP_DDS module plus the ardupilot_gz Gazebo packages; PX4's px4_ros_com and px4_msgs over its uXRCE-DDS bridge. This means a "control model" can be genuinely arbitrary robotics code someone else already published as a ROS2 node — you're not reimplementing swarm AI, you're wiring the sim up to run it.

Trade-off: this is real infrastructure — Linux (or WSL2), ROS2, and either ArduPilot/PX4 build tooling or Docker images for them, running somewhere the browser can reach over WebSocket. It's no longer a pure static page; it needs a machine (yours, or a small always-on server) running the sim backend.

TRACK 3Foundation-model controlOptional add-on to Track 2
Swap in a real foundation-model policy as one of the pluggable control models, instead of everything being hand-rolled or ROS2-only.

NVIDIA Cosmos 3 (confirmed real — see §06) ships a variant, Cosmos3-Edge (4B parameters), explicitly built for real-time robotic policy and real-time visual reasoning. Behind the same control-model contract from §04, one selectable model is "call this drone's state out to a Cosmos3-Edge inference endpoint and use its output as the command" — treated identically to a ROS2-bridged model, just with a foundation model instead of hand-written logic on the other end of the wire. Cosmos's world-generation/synthetic-video capabilities are also a separate, upstream option for producing richer training/test environments, distinct from anything in the live control loop.

Trade-off: even the 4B Edge variant is a real foundation model — GPU inference, not something that runs in a browser tab. Worth adding once Track 2's control-model interface is proven out and a trial specifically wants to compare a learned foundation-model policy against the scripted/PID/real-autopilot baselines.

04The pluggable control-model interface

The one piece of design that has to be right regardless of track, since it's the actual "insert and select for a trial" mechanism the request is asking for.

Define one contract that every control model implements, independent of how it's actually run:

  • Input (per tick): own state (position, velocity, attitude, battery), local sensor reads, and — critically — the current comms-link reading from the RF layer (signal quality, GPS-lock confidence, whether the uplink/downlink is currently jammed).
  • Output (per tick): a command — waypoint, velocity/attitude setpoint, or (for swarm models) a set of per-drone commands.
  • Metadata: a name, a short description, and which "class" it represents (manual scripted path, classical PID/guidance, in-browser learned/RL policy, ROS2-bridged external node, or a foundation-model policy call like NVIDIA Cosmos3-Edge — see §06) — so a trial log can say what was actually being tested, not just "model #3."

In Track 1 this is just a JS interface (a function or small class). In Track 2 it's the same contract satisfied by a ROS2 node, and in Track 3 by a call out to a foundation-model inference endpoint — the frontend doesn't need to know which track produced a given command, only that the shape is consistent, which is what makes all three tracks interchangeable behind the same selector UI later.

05Simulating RF channels and interference zones

This is the one piece with no mature off-the-shelf web library — confirmed this session, not assumed — so it has to be purpose-built regardless of which track is chosen.

A workable model, cheap enough to run every physics tick:

  • Baseline link quality: free-space path loss from each drone to its relay/GCS — signal falls off with distance, giving a natural "RF horizon" without any hand-authored zones.
  • Jamming/interference zones: author-defined volumes (spheres, extruded polygons) with a jam type — broadband noise (degrades general link quality), GPS-specific (kills position-fix confidence without touching the comms link), or directional (a cone from a fixed emitter). A drone's per-tick signal state is baseline minus whatever zones it's currently inside.
  • Feed into the control-model contract above: the comms-link reading is just another input field. A model that ignores it flies straight through a jam zone and loses link; a model that implements the Dronscape taxonomy's Contested-Link Autonomy tier (RF-horizon dive, GPS-denied dead-reckoning, self-healing mesh relay) visibly changes behavior at the zone boundary — which is the actual experiment.
  • Visualize it: render jamming zones as translucent volumes in the WebXR scene — in an immersive session you can physically walk/fly into one and watch the HUD's link-quality readout degrade in real time.

For higher fidelity later — real terrain-aware propagation instead of simple geometric zones — NS-3 is a real, current network simulator with genuine wireless/RF channel models (its ns-3.48 release added a ray-tracing channel model). It isn't browser-based, so the realistic path is running it offline to precompute a signal-strength/interference grid for a given terrain and radio layout, then importing that grid as static data the live sim reads from — not driving the simulation live. SPLAT! (terrain-based coverage prediction) is real but its last release was 2014 — usable for one-off precomputed coverage maps, not something to build a live pipeline around.

06Verdicts on the specifically-requested stacks

Direct answers to "is it worth reusing ROS2 / ArduPilot / Cosmos," now that all three are verified — including a correction on what "Cosmos" actually refers to.

ROS2Worth it if you want external code to plug in

Real value if the goal is letting genuinely external control-model implementations — someone else's published swarm-AI research code, most of which ships as ROS2 nodes — plug in unmodified. The browser-bridge story is solid and standard: rosbridge_suite (WebSocket+JSON bridge, ROS2-supported, actively maintained) with roslibjs as the browser client — this is the de facto standard pattern, not a one-off hack.

Cost: a real ROS2 environment (Linux/WSL2 or Docker) has to run somewhere. Not something a static GitHub Pages deploy can host by itself.
ArduPilot (SITL)Best single reuse candidate

ArduPilot is arguably the best-fit reuse target of the three, because SITL is specifically a pure-software simulation mode built for exactly this use case — no hardware, just the real flight-control firmware. It already has a real ROS2/DDS bridge (AP_DDS, part of the main ArduPilot repo) and a Gazebo integration (ardupilot_gz), and speaks MAVLink, which has a real, ArduPilot-org-maintained JS library (node-mavlink) — a legitimate, low-effort path to a direct browser↔autopilot link that doesn't require standing up ROS2 at all if you don't need it yet.

Also directly useful for the RF-interference ask: ArduPilot SITL already supports injecting failure conditions (simulated GPS glitch/loss, RC/telemetry loss) as parameters — real failsafe behavior you'd otherwise have to fake.

NVIDIA Cosmos 3High-value, heavyweight — corrected verdict

This is the real "Cosmos 3" the original request meant. An earlier draft of this doc mistakenly substituted an unrelated command/telemetry tool with a similar name — that mistake has been removed; this is the actual, drone-relevant thing. Confirmed directly against nvidia.com/ai/cosmos and the NVIDIA/Cosmos README: Cosmos 3 is an open, omni-modal physical-AI world-foundation-model platform, released in the Cosmos 3 Hugging Face collection on May 31, 2026. It's a unified Mixture-of-Transformers design — an autoregressive transformer for reasoning paired with a diffusion transformer for generation — spanning text, image, video, sound, and physical robot action in one model, across three sizes: Cosmos3-Super (64B, datacenter-scale synthetic data generation), Cosmos3-Nano (16B, balanced), and Cosmos3-Edge (4B, explicitly built for real-time robotic policy and real-time visual reasoning).

Two genuinely distinct uses for this simulator (see Track 3, §03): (1) as a pluggable control model itself — Cosmos3-Edge's stated purpose is real-time robotic policy inference, which is exactly the "insert and select an AI model" slot in §04, and a real foundation-model policy is a much more interesting trial subject than a hand-rolled PID controller; (2) as a world/environment generator — Cosmos's world-simulation and synthetic-video-generation capabilities could produce richer, more varied training/test environments than hand-authored scenes, upstream of the simulator rather than inside its render loop.

Cost: even the 4B Edge variant is a real foundation model — GPU inference, not something that runs in a browser tab like an ONNX-Runtime-Web policy. Realistically a Track-2-or-later addition: the sim calls out to a Cosmos3-Edge inference endpoint for that trial's control model, the same way Track 2 calls out to an ArduPilot SITL process.

07Recommended path

Phase 1 — Browser-native MVP (Track 1)

Three.js + WebXR scene, custom lightweight flight physics, the control-model plugin interface with two or three JS-native models to start (a scripted path, a simple PID-style guidance model, and one ONNX/TF.js learned policy), and the geofenced RF/jamming layer. Fully static — deployable in this repo exactly like every other demo, no backend to run or maintain.

Phase 2 — Real autopilot bridge (Track 2)

Once the control-model interface and RF layer are proven out in Phase 1, add ArduPilot SITL as an optional backend behind the same interface — either a direct node-mavlink bridge for a fast path, or a ROS2/rosbridge path if external swarm-AI nodes need to plug in. The WebXR frontend doesn't change; it gains a second source of "control model" that happens to be real firmware instead of a JS function.

Phase 3 — Foundation-model control (Track 3, optional)

Once Phase 2's interface is proven, add NVIDIA Cosmos3-Edge as another selectable control model via an inference-endpoint call — worth it specifically when a trial wants to compare a learned foundation-model policy against the scripted/PID/real-autopilot baselines.

Every tool named above was verified this session via direct WebFetch/GitHub-API/npm-registry calls against its real repo, docs, or release metadata — not recalled from training data.
