Variant Investigation

What is the ngrok link, and why did it behave differently?

This resolves the discrepancy from the main Performance Review: a reader's iPhone 12 Pro Max appeared to load the 3D tour fine in portrait, contradicting Finding 01 (every phone-width visitor is blocked). The device, resolution, and browser were all independently verified as accurate — the actual explanation is that the reader was looking at a different site entirely.

https://3404-212-20-115-15.ngrok-free.app/?area=019f3c2d-9baa-77b6-8f78-262ee5d83aeb&owner=019f463a-293c-74ac-986a-e84d65430581&bench=1&label=crowd
Checked 2026-07-29 ngrok-free.app tunnel — temporary, will expire/rotate Chrome (headless) via Puppeteer Not the audited production URL
Verdict

This is a developer's local Vite dev server, tunneled out via ngrok, running an in-progress branch of the same Horizon360/Bryto product — not the production build at horizon360.bryto.com. At the exact resolution in question (428×926, portrait), this build loaded the 3D scene normally with no mobile block. The mystery isn't a bug in this report's testing — it's that two different codebases were being compared.

What's actually being served here

The HTML response contains unmistakable Vite development-server signatures — /@vite/client, /@react-refresh, and source files served directly as .tsx rather than a bundled, minified main.js. A source file's embedded path even reveals the local machine it's running on: 

fileName: "C:/Users/david/Downloads/Antigravity/latest-main-2026-07-28/hawk/src/app/main.tsx"

That confirms the internal project codename is "hawk" (matching the bryto-hawk-web-data GCS/S3 bucket referenced elsewhere in the code), running from a Windows machine, checked out from main as of the date in the folder name. This is someone's live, currently-running local development build — not a stable or public artifact.

Built-in crowd-testing harness

The bench=1&label=crowd query parameters aren't incidental — they trigger a purpose-built performance harness embedded directly in the page. It hooks drawElements/drawArrays to count real WebGL draw calls, waits for the scene to visually settle, then measures FPS, frame-time percentiles, triangle count, estimated VRAM, JS heap usage, GPU model (via WEBGL_debug_renderer_info), device memory, and core count — and uploads the result to a /__bench endpoint labeled by whoever's testing it (here, "crowd").

In other words: the dev team appears to be running their own version of exactly what this report set out to do — gathering real, labeled, per-device performance data from actual testers. This link was very likely sent out for that purpose, which is probably how it ended up in front of a real iPhone 12 Pro Max in the first place.

Confirmed: no mobile block at the exact resolution in question

Loaded fresh at 428×926 (the same reader's device, verified earlier in this investigation), portrait, with the ngrok interstitial bypassed via the ngrok-skip-browser-warning header:

The scene didn't finish loading within the test window — plausibly the free ngrok tunnel's bandwidth, or a slower unminified dev build serving uncompressed assets from a local machine rather than a CDN. That wasn't chased further: hammering someone's personal dev tunnel for a full load-performance profile isn't an appropriate use of this access, and it isn't needed to answer the question that mattered — does the 768px gate exist here? It doesn't.

What this means for the main report

Finding 01 in the Performance Review stands as tested — it accurately describes horizon360.bryto.com, the URL that was actually specified as the audit target, and every number and screenshot there is still real and reproducible against that URL today. This variant simply explains the reader's differing experience: they were on a separate, in-development codebase, which appears to have already addressed the mobile gap this report flagged as the top-priority issue. If that's accurate, the practical recommendation shifts from "fix the bug" to "ship the branch that already fixed it" — worth confirming directly with whoever's running that dev server.

Raw investigation log

1. Initial reachability check

Plain curl against the tunnel, before any bypass headers:

$ curl -sSI --max-time 20 "https://3404-212-20-115-15.ngrok-free.app/?area=...&owner=...&bench=1&label=crowd"

HTTP/2 200
cache-control: no-cache
content-type: text/html
date: Wed, 29 Jul 2026 06:50:24 GMT
etag: W/"16e8-+6VyWnDTbUqUyyGyDZ6+j+2Rs30"
ngrok-agent-ips: 212.20.115.15
vary: Origin

The weak etag format (W/"...") is characteristic of Express/Vite's default static-file serving, not Google Cloud Storage's UploadServer — the first hint this wasn't the same infrastructure as the production site.

2. First automated fetch hit ngrok's own interstitial, not the app

A plain Puppeteer page.goto() returned ngrok's free-tier "you are about to visit" warning page instead of app content — expected behavior for automated clients without a prior "Visit Site" click. Bypassed with the documented header:

await page.setExtraHTTPHeaders({ 'ngrok-skip-browser-warning': 'true' });

3. Source fetch confirming Vite dev mode

$ curl -sS "https://3404-.../src/app/main.tsx" | head -c 400

import __vite__cjsImport0_react_jsxDevRuntime from
  "/node_modules/.vite/deps/react_jsx-dev-runtime.js?v=0bd0455f";
const jsxDEV = __vite__cjsImport0_react_jsxDevRuntime["jsxDEV"];
import "/src/app/instrument.ts";
import "/src/shared/i18n/index.ts";
import "/src/shared/utils/logger.ts";
import { ErrorBoundary, reactErrorHandler } from
  "/node_modules/.vite/deps/@sentry_react.js?v=0bd0455f";

A production build would never serve raw .tsx or Vite's internal ?v=-hashed dep-cache paths — these only exist when a Vite dev server is actively transforming source on request.

4. Launch test methodology at the exact reported resolution

await page.setViewport({ width: 428, height: 926, deviceScaleFactor: 3, isMobile: true, hasTouch: true });
await page.setExtraHTTPHeaders({ 'ngrok-skip-browser-warning': 'true' });
await page.goto(URL, { waitUntil: 'networkidle2', timeout: 30000 });
// waited 8s, then read back:
document.querySelectorAll('*').length        // 88
document.querySelector('canvas')             // null (still downloading)
document.querySelector('[class*="mobile"]')  // null
document.body.innerText.slice(0, 300)
// "Downloading the 3D scene…\n\n2D\nMap\nCommunity\nArtist's Impression: ...
//  [unreleased]\nMADE WITH VERGE3D TRIAL\nDo not show again"

No pageerror events fired at any point — a meaningful contrast with production, where the same viewport reliably throws the checkHalfFloatTex / getContext exception documented in the main report's Finding 01.

5. Why testing stopped there

The scene never reached a fully-loaded state within the test window. This wasn't chased further with repeated requests or longer timeouts: this tunnel points at one person's local machine on a free ngrok plan, not a production CDN built to absorb load — running a full multi-minute or repeated-load profile against it isn't a reasonable use of incidental access to someone else's dev environment, and it wasn't necessary to answer the one question this investigation needed to resolve: does the 768px mobile gate exist on this build? A single clean load already answered that.
