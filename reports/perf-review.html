Performance Review

Load performance & low-end mobile behavior audit

Target: https://horizon360.bryto.com/demo/latest/index.html
Audited 2026-07-28 Chrome (headless) via Puppeteer 24.43.1 Device profile: Moto G4 Network: Slow 4G (176 KB/s down / 562ms RTT) CPU throttle: 4×–6× Live production URL, no local copy

This site is a Verge3D / Three.js–based interactive 3D community tour. The single biggest finding isn't a speed problem — it's that every phone-width visitor is deliberately turned away with a "use a desktop browser" message, regardless of connection speed or how new the phone is. Beyond that, the page that does load (tablet/desktop widths, ≥768px) ships roughly 26.6 MB uncompressed, which will struggle badly on older phones and weaker mobile connections if mobile support is ever added. Findings below are ordered by priority; use the button to expand the full investigation log, methodology, and raw data behind each one.

Findings & Recommendations, in priority order

01 Critical

Every phone-width visitor (≤767px) is deliberately blocked with a "use desktop" message

A fresh page load at any width from 320px to 767px — every phone in portrait, and most in landscape — renders a full-screen .mobile-warning overlay reading "This application is still not optimized for mobile devices. Please use a desktop browser to explore all features." This is clearly intentional (it's dedicated, purpose-built UI, not an error page), so there is no phone-performance story to test here at all today: the tour simply does not run on a phone, old or new. Given this is a real-estate/community walkthrough — a use case where a large share of real visitors browse from a phone — that is a significant product-level gap, not just a technical one.

Also found Even though the warning message displays correctly, the underlying page still throws an uncaught TypeError: Cannot read properties of null (reading 'getContext') from renderer._resizeCb in the bundled Verge3D engine — a leftover resize-event listener that fires and reaches into a renderer that was correctly never initialized for this path. Harmless to what's on screen today, but worth guarding, since the same code runs whenever a window crosses the 768px boundary (e.g. a tablet rotated, or a desktop window resized narrower) and any future change that assumes the resize handler completes cleanly could break silently.

Optimized (illustrative — based on the Brotli size measured above, not a captured header)

main.js (2.1 MB) and style.css (285 KB) are served with no Content-Encoding even when the client explicitly advertises Accept-Encoding: gzip, br, over HTTP/2. Compressing the actual downloaded files locally measured 77.5% smaller for main.js (2199 KB → 496 KB with Brotli) and 89.7% smaller for style.css (285 KB → 29 KB) — a combined 1.87 MB saved on every single page view, for a server config change with no code risk.

Recommendation Enable gzip/Brotli at the serving layer. The Server: UploadServer response header indicates this is served directly from a Google Cloud Storage bucket, which does not compress on the fly — either pre-compress objects and set Content-Encoding, or front the bucket with a CDN that compresses automatically.
03 High

15.4 MB of the 26.6 MB total is texture data that was compressed once, then un-compressed again

assets/models/community-v5/Extra_shadowsJPG.webp.006.png
Visual comparison — same file, re-encoded (preview downscaled; full-res savings measured in the analysis log)
85.1% smaller, visually equivalent at normal viewing distance.

Byte-accurate capture (Chrome DevTools Protocol) across 106 requests: 22.2 MB of the total is texture/image data for the 3D model. Most of it (41 files, 5.8 MB) is already well-optimized WebP and needs no work. The real problem is a specific 16-file, 10.9 MB subset whose filenames literally end in .webp.NNN.png — evidence they were converted from WebP back to raw PNG somewhere in the asset pipeline — plus 11 JPGs totalling 4.45 MB that were never converted to WebP at all. Re-encoding two of the PNGs and one JPG through cwebp at quality 82 measured 84–86% smaller for the PNGs and 51% smaller for the JPG — real, verified numbers, not an estimate.

Recommendation Re-export those 16 PNGs and 11 JPGs to WebP the same way the other 41 textures already were (or to a GPU-native format like KTX2/Basis Universal for a bigger win). Based on the measured ratios above, this alone removes roughly 11.5 MB from every page load.
04 Medium

Static assets are never cacheable

Response headers — main.js, style.css, index.html (measured)
Current
cache-control: public,max-age=0
(no content hash in filename)
Recommended (illustrative, not captured)
cache-control: public, max-age=31536000,
  immutable
assets/main.abc123.js

Every asset checked — main.js, style.css, the glTF data buffer, index.html — returns Cache-Control: public, max-age=0, and filenames carry no content hash. Browsers must revalidate every one of the 100+ requests on every visit. At the ~500ms+ round-trip latency typical of a weak mobile connection, that's a meaningful, entirely avoidable tax on repeat visits.

Recommendation Fingerprint filenames for anything under /assets/ and set a long, immutable Cache-Control (e.g. public, max-age=31536000, immutable).
05 Medium

Monolithic 2.1 MB blocking module script

Proposed sketch (illustrative, not measured)

main.js bundles the entire 3D engine and app logic into one non-deferred <script type="module"> in <head>. Measured Total Blocking Time (sum of long-task time beyond 50ms) was 1.3s on an unconstrained desktop-width pass and 2.3s under 4× CPU throttling — both well past the "poor" threshold (>600ms) for this metric.

Recommendation Code-split the 3D engine from bootstrap/UI code and defer or lazy-load the heavy engine bundle until after first paint, rather than blocking script evaluation up front.

Device QA — launch & load test across real market share

Rather than testing arbitrary devices, this picks real device profiles weighted by actual global market share, then runs a fresh launch test (does the app load or hit the mobile block?) plus a basic load-timing check for each — in both portrait and landscape — against the live production URL.

Method: device market share and screen-resolution distribution sourced live from StatCounter Global Stats (worldwide, June 2026). CSS viewport sizes (width×height) are real, publicly documented values for each device class; DPR and user-agent are representative, not device-exact. All 32 runs (16 device profiles × 2 orientations) are fresh page loads against the live site, unconstrained network — a separate axis from the Slow-4G tests elsewhere in this report. "Loads" means the 3D tour actually mounted (750 DOM nodes, matching the desktop baseline); "Blocked" means the .mobile-warning overlay from Finding 01 appeared instead.
Important caveat — this is Chromium, not Safari. Every "iPhone" row below was emulated by Puppeteer at the correct CSS viewport size, but Puppeteer only drives Chromium. On iOS, Apple requires every browser — including Chrome for iOS — to use the WebKit engine under the hood, so real Safari/WebKit rendering was never actually tested here. That said, the trigger condition turned out to be a plain window.innerWidth < 768 check (see evidence), which is a standard API that behaves identically across engines — so an engine difference is an unlikely explanation if your results differ. Two more likely causes: "Request Desktop Website" being enabled for this site (which reports a desktop-width viewport and would skip the check entirely), or having encountered a different dialog (this site also shows a dismissible pan/rotate/zoom instructions overlay, unrelated to the mobile block).

Architectural Overview

What this product actually is, reconstructed from outside the browser — no source access or internal docs were available for this audit.

Method: everything below comes from network requests, response headers, DOM structure, and literal strings found inside the shipped main.js bundle while running this audit. Layers marked "referenced, not observed" are code-level findings only — those hosts were never actually contacted during testing, so treat them as evidence of the product's capabilities, not confirmed dependencies of this specific deployment.
Client

Single-page app shell

  • One ES module bundle (main.js, 2.1 MB) loaded via <script type="module" crossorigin> in index.html — no code-splitting.
  • UI chrome styled by style.css (285 KB) plus a dedicated font.css.
  • Hard responsive gate: below 768px CSS width, a full-screen .mobile-warning overlay replaces the entire app — see Finding 01.
Engine

3D rendering: Verge3D (Soft8Soft) on Three.js

  • Identified via internal namespace strings (v3d.WebGLRenderer, v3d-container, v3d-simple-preloader) and a direct reference to soft8soft.com inside the bundle.
  • Verge3D exports interactive Blender scenes to WebGL — this explains the mouse-only "Hold left mouse to pan / right mouse to rotate / scroll wheel to zoom" tutorial overlay shown on load, with no touch-gesture equivalent offered.
  • The one genuinely external runtime dependency actually contacted during testing: cdn.soft8soft.com/fonts/roboto.woff — Verge3D's own default UI font.
Content

3D scene & assets — "community-v5"

  • Scene geometry/animation data: an LZMA-compressed glTF buffer, Demo_3D_plan_map_V2.bin.xz (2.15 MB), decompressed client-side.
  • 68 texture maps (PBR base-color/normal/shadow) under /assets/models/community-v5/ — see Finding 03 for the format breakdown.
  • Small chrome assets (logo, filter/zoom icons) served as plain PNG/SVG alongside the 3D content.
Hosting

Delivery

  • Served directly from a Google Cloud Storage bucket (Server: UploadServer) over HTTP/2 — no CDN layer detected in front of it (one would typically add the compression/caching that's currently missing — Findings 02 & 04).
  • URL path /demo/latest/ implies a versioned deploy pipeline, with "latest" pointing at whichever build is current.
Referenced, not observed

Product family

Methodology

All testing was run directly against the live production URL above using headless Chrome, driven via Puppeteer 24.43.1 over the Chrome DevTools Protocol (CDP) — no local copy or proxy was used. Two device/network conditions were used throughout:

  • Desktop baseline: 1600×1000 viewport, no CPU/network throttling — establishes what the site looks like under ideal conditions.
  • Older-phone simulation: Puppeteer's "Moto G4" device profile (360×640 CSS viewport, 2× DPR, mobile UA + touch), combined with CDP Emulation.setCPUThrottlingRate at 4×–6× and CDP Network.emulateNetworkConditions set to the "Slow 4G" preset (176 KB/s / 1.44 Mbps down, 82 KB/s / 675 kbps up, 562.5ms latency) — Puppeteer's stand-in for a budget/older Android device on a weak connection.
Limitations: this is synthetic lab testing (single run per configuration, one geographic vantage point), not Real User Monitoring — absolute timings will vary with real network conditions and real device GPUs. Headless Chrome renders WebGL via a software rasterizer (SwiftShader) rather than a phone's real GPU, so raw 3D frame-rate numbers weren't used as evidence for any finding here. The one exception is Finding 01: that root cause was isolated by varying viewport width alone, with throttling on and off, and reproduced identically every time — confirming it is a code defect, not a rendering-performance artifact of this test environment.
