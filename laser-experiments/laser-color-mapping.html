Color → xTool Power Mapping

What a swatch color means in this app, and how far that meaning actually reaches.
In one line: in most tabs a color is a laser power setting (chosen from a calibrated palette); in Shape Fill, colors are decorative by default, but you can now switch to a real laser palette to preview the pattern in achievable burn colors — that preview still isn't an export yet.

Summary

Most Pattern Tool colors come from a palette file where every swatch is really "this is what N% laser power looks like burned into real material."

2

Details — the real xTool pipeline
How the rest of the app works

Most tabs in the Pattern Tool (Flower of Life, Mandala, Voronoi, etc.) don't let you pick an arbitrary color. They let you pick a palette — a small JSON file under pattern-tool/palettes/*.json — where every swatch is a calibration entry: an RGB color paired with the laser power that produced it on a specific material, at a fixed speed and line density (LPCM). laFont-1000lpcm.json, for example, is a 21-step power sweep on brushed <1mm SS304 stainless at 200 mm/s, 1000 LPCM:

SwatchLabelPower
#d4bc4aPale Straw16%
#c88010Gold20%
#b06030Amber24%
#601098Violet30%
#0858b8Blue38%

So when a tool's "Color" control shows you a Gold swatch, it isn't a decorative choice — it's a stand-in for "burn this shape at 20% power." Speed, LPCM, and repeat count come from the same JSON, at the palette level or per-entry.

The code path, end to end

palette JSON
{ rgb, power, speed, lpcm, repeat } → PalMgr.getParams(paletteId, idx) → XCSExporter.addPath/addCircle({ layerColor, params, laserSource }) → XCSItem.createDisplayNode → project.toJSON() → .xcs file
  • PalMgr.getParams(paletteId, idx) (pattern-tool/js/palettes.js) reads one entry from the loaded palette and returns { power, speed, density, repeat, processingLightSource } — falling back to the palette's own defaults, then hard-coded defaults, if an entry omits a field.
  • Each drawing call passes that straight through: XCSExporter.addPath(project, { layerColor: entry.rgb, laserSource, params, isFill, ... }). layerColor is the entry's RGB; params is what getParams() returned.
  • XCSItem.createDisplayNode (xcs-module/js/xcs-system.js) uses that same RGB as the shape's layerTag — every shape sharing a color is grouped into one xTool layer — and merges params into that item's parameter.customize (power/speed/density/repeat/processingLightSource).
  • project.toJSON() serializes the whole thing; XCSExporter.exportProject() downloads it as a real .xcs file. Opening that file in xTool's own software shows exactly those layers, each already carrying the power/speed/repeat baked in above — nothing needs to be re-entered by hand.
Details — Shape Fill's Laser Palette / True Color / Color Mapping

What the new controls actually do

Shape Fill's Style section now has three related rows: Laser Palette, then Color Mapping, then Mode. Laser Palette is the exact same palette-picker widget every other tab uses (UI.makePaletteSelector) — it lists the same real, calibrated laser palettes from App.palettes — plus one extra entry that isn't a real palette at all: ★ True Color.

  • True Color (default): Color Mapping's decorative colors — SteamPunk's browns and golds, Autumn Leaves' oranges, etc. — are drawn exactly as defined. Nothing is substituted. This is how Shape Fill always worked before this control existed.
  • A real laser palette selected: for each color in the current Color Mapping list, the app finds the closest-matching entry in that laser palette (by plain RGB distance) and substitutes it — with one rule: no two Color Mapping colors are ever matched to the same laser entry. Each gets assigned the nearest one still unclaimed, so a 9-color style palette matched against a 21-entry laser palette comes out as 9 distinct real swatches, not a handful repeated.

Hovering the Color Mapping label shows a popout listing every true color — and, when a laser palette is active, what real swatch and power percentage it was matched to — so you can see the substitution before it's drawn.

Where this stops short of a real export

Be precise about what changed: Shape Fill draws directly onto an HTML <canvas> with ctx.fillStyle/ctx.strokeStyle — it still never builds an XCSProject, never calls XCSExporter, and still has no "Export XCS" button. Selecting a laser palette only changes which hex strings the canvas is painted with, so the preview shows colors that are actually achievable at a known power on real material — it does not attach power/speed/layer data to anything, and there is still no way to turn a Shape Fill pattern into a laser-ready .xcs file. Closing that gap would still mean teaching Shape Fill to emit real vector paths and running those through XCSExporter with per-color params from PalMgr, the way every other tab already does.
